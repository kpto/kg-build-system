# Edit-Time Code Generation — Temporary Specification

## 1. Status and purpose

This is a temporary design specification for edit-time code generation in the
Knowledge Graph Build System. It records the current direction so that an
initial implementation can be explored without treating every detail as part
of the stable public API.

Code generation is a largely separate system from graph compilation and build
execution. It is invoked as a development command and may run continuously as
a file watcher. Its purpose is to make declarations derived from provider-owned
inputs practical to author while keeping the resulting runtime Python code
explicit, inspectable, and version-controlled. The core generator does not
interpret or assign domain meaning to provider configuration or dependencies.

The generator must not defer declaration construction until blueprint or build
compilation. Compilation consumes normal Python declarations that already
exist in the project.

## 2. Design goals

- Generate ordinary runtime Python, not only type stubs.
- Keep generated code visible and reviewable as an official project artifact.
- Avoid runtime class mutation, hidden field injection, and compilation-time
  generation.
- Make only a small, predictable change to an author-owned declaration file.
- Confine subsequent generated changes to clearly identified sidecar modules.
- Preserve handwritten decorators, bases, class bodies, comments, and
  formatting.
- Support deterministic one-shot generation, continuous watching, and CI
  freshness checks.
- Report source locations and actionable diagnostics without importing
  partially generated project modules.

## 3. Non-goals for the initial extension

- Generation during `create_blueprint`, `compile_blueprint`, or `build`.
- Runtime discovery or interpretation of provider dependencies.
- Dynamic population of an empty class by a decorator or metaclass.
- Generating only `.pyi` files while reconstructing runtime declarations later.
- A stable plugin API for every possible generation provider.
- Automatically migrating arbitrary handwritten declarations.

## 4. Authoring model

An author initially marks an empty or handwritten declaration with the
generation decorator:

```python
from kg_build_system import Table, generated


@generated(...)
class TargetTable(Table):
    ...
```

The first generation pass creates a generated sidecar containing a plain
Python mixin and minimally wires that mixin into the declaration:

```python
from kg_build_system import Table, generated

from ._generated.target import G_TargetTable  # noqa: E402  # isort: skip


@generated(...)
class TargetTable(G_TargetTable, Table):
    ...
```

The generated sidecar contains ordinary runtime declarations:

```python
# Generated by kg-build-system. Do not edit manually.

from kg_build_system import Field, field


class G_TargetTable:
    id: Field[str] = field()
    approved_symbol: Field[str] = field(name="approvedSymbol")
```

`TargetTable` remains the public, final declaration. `G_TargetTable` is a
generated implementation detail and is not itself a concrete `Table`.

### 4.1 Why generated mixins

Python has no partial-class facility. Supplying generated members without
editing the public class therefore requires inheritance, runtime mutation, or
metaclass behaviour. A generated plain mixin provides explicit runtime code
without introducing hidden declaration construction.

This also follows the framework rule that ordinary Python mixins may provide
reusable table or graph shapes while final layer classes establish declaration
identity.

### 4.2 Generated module layout

Generated modules should live in a private sibling package:

```text
contracts/
  target.py
  _generated/
    __init__.py
    target.py
```

One generated sidecar per authored module is the default. A sidecar may contain
multiple generated mixins when its authored module contains multiple generated
declarations.

Names such as `x.generated.py` must not be used because a dot in a filename
does not form a normally importable Python module. The private `_generated`
package makes ownership and import semantics explicit.

## 5. Source mutation contract

The generator owns generated sidecar files. In an author-owned source file it
may modify only the integration required to connect a marked declaration to
its sidecar:

1. Add or update the generated-mixin import immediately before the complete
   decorator stack.
2. Add, update, or remove the corresponding generated mixin in the class base
   list.

It must preserve:

- every non-generation decorator and its order;
- every handwritten base and its relative order;
- class docstrings, options, fields, methods, and nested declarations;
- comments and formatting unrelated to the integration edit;
- file encoding and line-ending style.

The import remains next to the class deliberately. It carries import-organizer
directives so automated lint fixes do not move it:

```python
from ._generated.target import G_TargetTable  # noqa: E402  # isort: skip
```

The implementation must use a concrete syntax tree rather than round-tripping
the file through Python's `ast` module. Writes must be atomic. A failed render,
validation, or formatting operation must leave the previous files intact.

## 6. Decorator semantics

`generated(...)` is primarily a static generation marker and configuration
carrier. At runtime it must not create fields, modify bases, resolve provider
dependencies, or invoke a generator. It may attach non-secret generation
provenance to the already constructed class, provided it returns the same class
object.

### 6.1 Stacked decorators

The generation decorator must be the topmost decorator:

```python
@generated(...)
@registered
@some_transform(...)
class TargetTable(G_TargetTable, Table):
    ...
```

The generated import is inserted before the entire decorator stack. The
generator changes only the class bases and preserves the stack exactly.

Requiring `@generated(...)` to be outermost ensures that any runtime
provenance is attached to the final object returned by inner decorators. It
also gives generated declarations a consistent visual form.

### 6.2 Static decorator validation

Decorator validation happens from source syntax before project modules are
imported. For every class, the generator resolves decorator qualified names
and applies these rules:

- no matching decorator: ignore the class;
- exactly one match at decorator position zero: valid;
- exactly one match at any other position: error;
- more than one match: error.

Supported spellings may include direct, qualified, and aliased imports, but
they must resolve to the framework's canonical decorator rather than merely
having the local name `generated`.

Example diagnostics:

```text
contracts/target.py:14: TargetTable has multiple @generated decorators
contracts/disease.py:27: @generated must be the topmost decorator on DiseaseTable
```

Static validation is required because decorator ordering cannot be reliably
recovered after decorators have executed.

## 7. Base ordering and overrides

The default transformation places the generated mixin before handwritten
mixins and the final layer base:

```python
class TargetTable(G_TargetTable, AuditedTableMixin, Table):
    ...
```

The exact override rules must be tested against declaration collection and
documented before the API is stabilised. The intended author experience is
that handwritten members on the public declaration may override generated
members explicitly, while accidental duplicate external names are diagnosed.

Generated bases must ordinarily be plain mixins. A generator may use a
framework template base only when the generated shape itself requires
framework metadata, and only if doing so does not create a concrete table,
struct, projection, node, or edge declaration.

## 8. Command model

The initial command surface is:

```text
kbs generate          perform one deterministic generation pass
kbs generate --watch  watch relevant files and regenerate after changes
kbs generate --check  make no changes; fail if output is missing or stale
```

The watcher is an authoring convenience, not required build infrastructure.
CI and release workflows use `--check`. Compilation never repairs generated
code automatically.

### 8.1 Working directory

The command operates on a configured project working directory. It discovers
Python source files within that boundary and must not follow paths outside it
unless an explicitly configured generator input permits read access.

Generated output paths must resolve inside the project. The generator must
reject path traversal, output collisions, and attempts to overwrite files it
does not own.

### 8.2 Watch inputs

The watcher performs one complete discovery and generation pass at startup,
then builds an in-memory dependency index. A provider declares the project
paths on which each generation request depends; the core assigns no schema,
configuration, or other domain meaning to those paths.

The watcher observes:

- Python modules containing generated declarations;
- paths explicitly declared by providers as dependencies.

After startup, event batches are processed incrementally:

- a changed authored Python module is rescanned and its dependency-index entry
  is updated;
- a changed provider-declared dependency regenerates only its dependent
  authored modules;
- a changed generated sidecar is ignored because generation is one-way;
- an event for an unknown path is ignored rather than causing a full scan.

File events are debounced and coalesced. One-shot generation and `--check`
remain complete project operations. Watch mode uses the same rendering,
validation, ownership, and installation implementation on the affected subset;
it does not use a weaker generation path.

## 9. Discovery without importing project code

The command initially discovers generation requests through static Python
source analysis. This allows it to process the initial empty declaration even
when its generated module does not exist yet.

Generation configuration accepted in decorators must therefore have a
statically interpretable form for the initial implementation. Arbitrary Python
execution in decorator arguments is outside the initial scope. Unsupported
expressions produce a diagnostic rather than causing the project module to be
imported.

A later design may introduce explicitly importable provider configuration, but
provider loading must remain separate from importing the user's declaration
module.

## 10. Determinism, ownership, and freshness

Every generated sidecar contains an ownership header and sufficient provenance
to reproduce or validate it. A generation result should be derived from:

- the normalized generation request;
- relevant provider implementation version;
- relevant external input content;
- rendering format/version.

The system computes a stable fingerprint over these inputs. `--check` fails
when:

- a marked class is not wired to a generated base;
- a generated import or sidecar is missing;
- the generated base does not match its public declaration;
- the recorded fingerprint is stale;
- the current generated content differs from deterministic rendering;
- a generated output path is owned by a different request;
- the source contains invalid decorator placement or duplicate generation
  decorators.

Generated files are expected to be committed to version control. Manual edits
are detectable as freshness failures. Normal generation must not silently
overwrite an unexpectedly modified generated file unless ownership and policy
permit it; a separate explicit force or recovery operation may be added later.

## 11. Formatting and validation

Generation occurs as a transaction:

1. Discover and validate generation requests.
2. Ask each provider for its declared dependencies and normalized output.
3. Render sidecars and source integration edits in memory.
4. Parse every rendered Python module.
5. Validate declaration names, imports, bases, and ownership.
6. Optionally format generated output using the configured formatter.
7. Atomically commit all successful changes.

Formatting tools are never permitted to rewrite unrelated author-owned code as
a side effect of generation. A formatter failure aborts the transaction.

The initial implementation should include tests covering:

- first generation of an empty declaration;
- idempotent repeated generation;
- sidecar changes after a provider dependency change;
- stacked decorator preservation;
- misplaced and duplicate generation decorators;
- direct, qualified, and aliased decorator imports;
- preservation of handwritten bases and class bodies;
- missing, stale, and manually altered generated files;
- multiple declarations in one authored module;
- import placement under formatting and lint fixes;
- watcher dependency indexing, incremental regeneration, event coalescing, and
  ignoring generated-sidecar and unknown-path events;
- rollback when any request in a pass fails.

## 12. Compilation relationship

Blueprint and build compilation consume the public declaration exactly as
normal Python:

```python
class TargetTable(G_TargetTable, Table):
    ...
```

The framework's existing declaration machinery collects fields inherited from
the generated mixin. Compilation does not read generation requests or provider
dependencies and does not synthesize missing declarations.

Compilation may validate recorded generation provenance and reject an
obviously incomplete or stale declaration with an actionable message:

```text
TargetTable has stale generated code; run `kbs generate`
```

Whether compilation performs this freshness check by default remains an open
decision. `kbs generate --check` is the canonical complete validation.

## 13. Initial vertical slice

The proof of concept uses a deliberately minimal `dummy` provider. It reads a
small provider-owned JSON format and demonstrates required and nullable scalar
fields, external names, descriptions, deterministic regeneration, and naming
collision diagnostics. This format is test infrastructure, not a public schema
standard or a source of domain concepts for the core generator.

The core provider contract is generic. Every provider implementation declares
a frozen, strict, keyword-only configuration model:

```python
class ProviderGenerationConfig(BaseModel):
    ...


class Provider[T: ProviderGenerationConfig](ABC):
    ID: ClassVar[str]
    VERSION: ClassVar[str]
    CONFIG_TYPE: ClassVar[type[ProviderGenerationConfig]]

    @classmethod
    def dependencies(cls, context: ProviderContext[T]) -> tuple[Path, ...]: ...

    @classmethod
    def generate(
        cls, context: ProviderContext[T], *, generated_name: str,
    ) -> GeneratedModule: ...
```

A provider:

- declares the project paths on which a request depends;
- returns a provider-independent normalized declaration model;
- owns all interpretation of its configuration and dependency contents.

The first slice is successful when generated declarations are ordinary
importable Python and compile through the existing blueprint path. Richer
providers may later add nested structs, collections, annotations, or external
metadata formats without changing discovery, watching, rendering, or build
compilation.

## 14. Open questions

- The final public names and import locations of `generated` and the CLI.
- Whether the decorator should attach runtime provenance or be a strict
  identity decorator.
- The concrete syntax tree library and formatter integration.
- Exact handwritten-versus-generated member override rules.
- Whether source integration imports need explicit marker comments in addition
  to their deterministic structure.
- Whether generated files should be overwritten automatically when their
  content was manually changed but their ownership is unambiguous.
- Whether compilation checks freshness or leaves that exclusively to
  `kbs generate --check`.
- Evolution of the provider-independent normalized declaration model beyond
  the dummy proof of concept.

## 15. Module parsing and source transformation

The initial implementation should parse and edit Python modules with a
concrete syntax tree library such as LibCST. Python's `ast` module is suitable
for semantic analysis but cannot reliably preserve comments, blank lines,
whitespace, or exact formatting.

The transformation pipeline is:

```text
read source
  -> parse concrete syntax tree
  -> resolve imports and decorators
  -> validate generation requests
  -> calculate desired sidecars and source wiring
  -> transform trees in memory
  -> render and reparse every result
  -> compare in --check mode or write safely
```

### 15.1 Parse without importing project modules

Given:

```python
from kg_build_system import Table
from kg_build_system.code_generation import DummyGenerationConfig, DummyProvider
from kg_build_system.generation import generated as codegen


@codegen(DummyProvider, DummyGenerationConfig(source="../../fields.json"))
@registered
class TargetTable(Table):
    ...
```

the command reads the file as text and creates a concrete syntax tree. It also
requests source-position and qualified-name metadata from the parser.

The project module is never imported during discovery or source rewriting.
This permits first generation before the sidecar exists, avoids arbitrary
project import side effects, and allows useful diagnostics when other modules
are temporarily incomplete.

Only module-level generated classes are supported initially. A generated class
nested in a function or another class is rejected because its import placement
and runtime identity are less predictable.

### 15.2 Resolve the generation decorator

A configured decorator call may use direct, qualified, or aliased imports:

```python
@generated(DummyProvider, DummyGenerationConfig(...))
@kbs.generated(providers.DummyProvider, providers.DummyGenerationConfig(...))
@codegen(ProviderType, ConfigType(...))
```

For a call, discovery examines its function expression. Qualified-name
resolution determines whether that expression refers to the framework's
canonical public decorator. Text matching alone is insufficient because an
unrelated package may also export a decorator named `generated`.

Direct, qualified, and aliased imports may be supported, provided they resolve
to the canonical public identity. The scanner records the source path, class
name, source position, decorator position, and normalized generation request.

For each class it collects all decorators resolving to `generated` and applies
the rules in section 6.2. Decorators are stored in source order, so position
zero is the topmost decorator.

### 15.3 Evaluate decorator arguments statically

The first API should constrain decorator arguments to statically readable
values:

```python
@generated(DummyProvider, DummyGenerationConfig(source="../../fields.json"))
```

Initially supported values are strings, numbers, booleans, `None`, and nested
lists, tuples, or dictionaries composed from supported values. Arbitrary calls,
attribute reads, environment access, and computed expressions are rejected:

```python
@generated(DummyProvider, make_config())                 # rejected
@generated(DummyProvider, CONFIG)                        # rejected
@generated(DummyProvider, DummyGenerationConfig(source=find_input()))  # rejected
```

The implementation uses a small syntax-tree evaluator and never `eval`.
Unsupported syntax receives a diagnostic at the argument's source location.
The provider and configuration types are resolved to import coordinates. The
generator imports the provider module, verifies the provider's `CONFIG_TYPE`,
and reconstructs the configuration with `model_validate`. It never imports the
user's declaration module.

### 15.4 Derive deterministic wiring

For `contracts/target.py` containing `TargetTable`, the default derivation is:

```text
sidecar:        contracts/_generated/target.py
generated base: G_TargetTable
import module:  ._generated.target
```

The expected source wiring is:

```python
from ._generated.target import G_TargetTable  # noqa: E402  # isort: skip


@generated(...)
class TargetTable(G_TargetTable, Table):
    ...
```

The mapping must be deterministic. Colliding output paths, generated class
names, or declaration identities are errors discovered before any write.

### 15.5 Inspect existing wiring and ownership

Before transforming a declaration, the command determines whether:

- its generated base is already present;
- that base is imported from the expected sidecar;
- the adjacent generated import is missing, correct, or conflicting;
- a different declaration claims the same generated symbol;
- the existing sidecar is owned by the expected request.

Expected states and actions are:

| State | Action |
| --- | --- |
| No import and no generated base | Perform first-time wiring |
| Correct import and base | Leave the authored source unchanged |
| Correct base but missing import | Repair the import |
| Correct import but missing base | Repair the base list |
| Generated symbol imported from a different module | Diagnose and stop |
| Multiple generated bases | Diagnose and stop |
| Generated name collides with another symbol | Use a specified deterministic alias policy or diagnose |
| Sidecar content differs from deterministic rendering | Report stale or manually altered output according to policy |

A name beginning with `G_` does not prove generator ownership. Ownership is
established from the import target, sidecar header or manifest, and normalized
request identity before an existing import or base may be replaced or removed.

### 15.6 Insert the import before the complete decorator stack

In a concrete syntax tree, decorators are part of the class definition rather
than independent module statements. Inserting an import as a module sibling
immediately before the class therefore places it before every stacked
decorator.

Conceptually, the transformer replaces one class statement with a flattened
sequence:

```text
generated import
updated class definition
```

It constructs the import as syntax nodes rather than concatenating source
text. The emitted statement is:

```python
from ._generated.target import G_TargetTable  # noqa: E402  # isort: skip
```

Comments attached to the declaration must remain with the declaration. For
example, this input:

```python
# Target records used by the public graph.
@generated(...)
class TargetTable(Table):
    ...
```

must become:

```python
from ._generated.target import G_TargetTable  # noqa: E402  # isort: skip


# Target records used by the public graph.
@generated(...)
class TargetTable(G_TargetTable, Table):
    ...
```

and not move the descriptive comment above the generated import. Preservation
of leading comments and blank lines requires dedicated golden-file tests.

### 15.7 Update only the generated class base

Given:

```python
class TargetTable(AuditedMixin, Table):
    ...
```

the default transformation is:

```python
class TargetTable(G_TargetTable, AuditedMixin, Table):
    ...
```

The transformer changes only the class base list. If the correct base is
already present, it makes no change. It may replace an outdated base only when
ownership has been proven; it must never remove an arbitrary base merely
because its name begins with `G_`.

All decorators, type parameters, class keywords, body statements, comments,
and handwritten bases remain unchanged. Exact override and generated-base
ordering rules remain subject to the decision in section 7.

### 15.8 Multiple generated declarations in one module

One authored module may contain multiple generated declarations, with one
sidecar containing all corresponding generated mixins. To keep each import
next to its class, imports remain separate:

```python
from ._generated.association import G_EvidenceStruct  # noqa: E402  # isort: skip


@generated(...)
class EvidenceStruct(G_EvidenceStruct, Struct):
    ...


from ._generated.association import G_AssociationTable  # noqa: E402  # isort: skip


@generated(...)
class AssociationTable(G_AssociationTable, Table):
    ...
```

The generated sidecar may contain:

```python
class G_EvidenceStruct:
    ...


class G_AssociationTable:
    ...
```

The import-organizer directive prevents consolidation or relocation. An
integration test must run the supported formatter and linter fix commands and
confirm that generated imports remain adjacent to their declarations.

### 15.9 Render sidecars from a normalized model

A provider should return a provider-independent normalized declaration model
rather than source text. Conceptually:

```text
GeneratedClass
  name
  declaration identity
  members

GeneratedField
  Python name
  external name
  declaration kind
  value type
  nullability
  description
  annotations
```

A Python renderer converts this model into a sidecar syntax tree or tightly
controlled template output that is immediately reparsed. Sidecars include an
ownership header containing the source declaration, provider identity, stable
fingerprint, and a generated-file warning. Fingerprints must not contain
machine-specific absolute paths.

### 15.10 Validate the complete desired state in memory

Before writing, the command:

1. Renders every updated author-owned module in memory.
2. Renders every generated sidecar in memory.
3. Reparses all rendered modules.
4. Confirms each public declaration has exactly one correct generated base.
5. Confirms every generated import resolves to an expected generated symbol.
6. Confirms every imported symbol is defined by its sidecar.
7. Confirms output paths and ownership identities do not collide.
8. Optionally formats temporary copies with the configured formatter.
9. Reparses the formatted result.
10. Repeats in-memory generation to verify idempotence.

A later validation layer may import generated modules in an isolated
subprocess, but source discovery and transformation must not require that.

### 15.11 Safe multi-file writes and recovery

All desired changes are computed and validated before the first destination is
replaced. Each new file is written to a temporary file in its destination
directory, flushed, closed, and installed with an atomic single-file replace.

Filesystems do not generally provide an atomic transaction across multiple
files. The command therefore writes generated sidecars before public source
wiring, makes every pass idempotent, and records enough ownership information
to detect and repair a partially completed pass. A small journal or manifest
may be introduced if crash recovery requires it.

Writing sidecars first ensures a normally interrupted pass does not leave a
public source file referring to a sidecar that was never created.

### 15.12 Shared desired-state implementation and incremental watching

One-shot and check modes compute complete project state. Watch mode computes a
complete baseline once and then applies the same desired-state implementation
to indexed affected requests:

```text
generate          desired state -> disk
generate --check  desired state <-> disk
generate --watch  full baseline -> dependency index -> affected subsets
```

`--check` must not use a second, weaker validation implementation. It renders
the exact desired files in memory, compares them with disk, reports concise
diffs and diagnostics, and exits unsuccessfully if any source wiring or
sidecar is missing, stale, or different.

The watcher must not rediscover the complete project after every event. It
updates the index when an authored Python module changes and regenerates only
modules selected by provider-declared dependency paths. Generated-sidecar
events and unknown-path events are ignored. Installing generated output must
therefore neither trigger reverse generation nor cause an output loop.
