# Workflow subpackage specification

The `kg_build_system/workflow/` package: how a workflow is declared, assembled, frozen into a
contract, and run.

| File | Role |
|---|---|
| `models.py` | The data an author declares and the runtime results: steps, openings, types, outcomes, report |
| `assembler.py` | Assembles the contributed steps into a workflow definition |
| `identity.py` | The names and identities a step and its openings go by |
| `contracts.py` | Freezes a workflow definition into a contract and fingerprints it |
| `ir.py`, `mapping.py` | Serialisable form of the same data, and the round trip |
| `interfaces.py` | What an executable module must provide |
| `services.py` | Runtime capabilities handed to a module |
| `executor.py` | Runs a contract and writes the report |
| `monitor.py` | Progress reporting hooks |

Module compilation into contributions lives in `kg_build_system/compile/`.

## 1. Vocabulary

An author works with modules, steps, inputs, outputs, artifact types, connections and a workflow
definition. A step carries its own eagerness and knows nothing about which module wrote it, because
the contribution around it says so.

The assembler's own words stay inside it: port, expansion, sequence, rank, endofunctor, producer,
unknown, admissible, fed, read, complete. A module author meets none of them.

Two verbs at the author's level: a step declares what it takes as inputs and what it gives out as
outputs. Inside the assembler a connection *feeds* an input's port and *reads* an output's port.

## 2. Declaration

```python
WorkflowStep(inputs, outputs, name=None, assembly_preference="eager")
    inputs:  tuple[Input, ...]
    outputs: tuple[Output | Publication, ...]

Input(type, name=None)        — takes one output of the type it names; a type holding `*` is an open
                                input taking one output of each type it matches, and which output
                                feeds each is the assembler's decision
Output(type, name=None)       — writes one value of that type; something must read it
Publication(type, name=None)  — hands a value to the build; nothing need read it
ArtifactType(namespace, name) — the type an input or output carries, either half of which may hold `*`

WorkflowContribution(module: ModuleDefinition, steps, variables)
    variables — opaque data the contributing module's executor reads
```

A step is declared inside the contribution of the module that wrote it, so it carries no module
reference: the grouping is what knows. A name is optional everywhere — an unnamed step takes its
position within its module, an unnamed input or output takes its kind word — and each is unique among
its siblings. Identity is always generated by putting the names together: a step is `module_id.name`,
an input or output is its step's identity with its own name on the end.

An input names a type, and `*` in it matches any run of characters, so one declaration spans a family
of types: `core / graph.*` is every graph-record type core writes. A wildcard belongs to a question,
so an output and a publication name one concrete type.

The declared data is amnesic. A step holds its inputs, outputs, name and eagerness; an input, output
or publication holds a type and a name. Nothing holds a reference to its owner, an identity that
could be derived, or a closure. Everything a step declares is data, so everything about a step reaches
the contract.

`assembly_preference`, `eager` or `deferred`, is the step's own statement of when it runs relative to
the others. The author's influence over wiring stops there: position in the composition and eagerness
become rank (§4), and nothing an author supplies picks a producer.

A publication is declared among the outputs because the step gives it out, and it is exempt from the
rule that every output is read: it exists for the build's result and has no reader inside the
workflow. Publication is read off the declared kind, never guessed from a type name.

`variables` belongs to the module rather than the step, and no rule reads it. A module that needs
per-step instruction data keys it by step name inside its own variables, and its executor is handed
that data once at construction.

## 3. Ports and expansion, internal to the assembler

The assembler turns each declared input and output into a numbered port, and expands an open input
into one port per type it matches. Available types are the types of every output, in first appearance
order. Output ports come first, in contribution order, then step order, then within each step's
outputs; input ports follow in the same walk, then within each input, then in available-type order
inside an open input. An expanded port is named after the input that grew it with the matched type on
the end, `name:type`, so an open input's ports are neighbours wherever ports are listed.

Ports of one step share that step's rank, so their order in this numbering is what decides which is
scanned first and which is preferred when the rank cannot separate them.

Expansion refuses two steps of one module with the same name, and the same name twice in one direction
on one step, because every explanation the assembler gives names a port by those strings. A clash
arising from expansion is refused the same way, and a step with a clash contributes nothing rather than
half its inputs. Both refusals raise `AssemblyError`.

## 4. Rank, internal to the assembler

Rank is one integer per step; a greater rank means the step runs earlier. It is the only ordering the
rules use and it refuses nothing: it enters one rule, to say which writer a reader takes. Nothing gates
on rank and no step is skipped because of it.

Rank is derived from position, module first, then eagerness, then order within the module:

```
(module index, eager before deferred, step index)   — earliest running has the greatest rank
```

So a step in an early module runs before any step in a later one whatever its eagerness, and core,
composed last, runs after every module's steps.

## 5. Assembly

`assemble(contributions)` assembles the contributed steps into a `WorkflowDefinition`, or reports what
it could not settle. Two phases run in this order because everything in the first holds of every valid
graph and must not be preempted by preference.

**Unavoidable.** Repeatedly, until nothing is left to deduce: an unfed port with exactly one admissible
writer is fed by it; an unread output with exactly one admissible unfilled reader reaches that reader.
One deduction at a time, so each is true of the wiring at the moment it is used.

**Concluded.** Scan unfilled ports, earliest step first, restarting from the top after every
connection, and make the first connection the rules conclude. For one input port, in order:

1. Drop every candidate that would close a cycle. No candidates at all, or none left, means this input
   can never be fed and no complete graph exists.
2. If any survivor is unknown, conclude nothing yet.
3. Otherwise take the endofunctor that ran last before the input, which is the freshest result the
   input could have in hand.
4. Otherwise the producers qualify. Two or more differ by nothing the declaration can weigh, so the
   declaration is indeterminate; exactly one is the answer.
5. Otherwise there is nothing legitimate to connect yet.

A category is what an output's step does to the type it writes, decided by walking the step's
dependency — the step plus everything chained ahead of it — asking whether any input in it takes that
type. Taking it makes the step an endofunctor over that type; a finished walk finding nothing makes it a
producer; a walk stopping at an input nothing feeds leaves it unknown. An unknown is a different fact
from a finished walk that found nothing, so it stops a conclusion without blocking others.

**Completeness.** A wiring is complete when every input port is fed and every `Output` is read.
Complete means `assemble` returns a definition: the contributions it assembled, in composition order,
with the connections between them. Otherwise it returns the connections it did make, with a reason for
every input left unfilled in scan order and the name of any output nobody reads. A refusal is never an
error inside the run: it wires all it can and says where it stopped and why. `compile` turns an
incomplete result into a build failure carrying those reasons, which is also how an indeterminate
declaration reaches the author — named by the rival outputs the declaration could not separate.

**Cardinality.** An input takes one feeder: two writers for one input is the ambiguity these rules
settle, not something to record. An output may have any number of readers and must have at least one; a
publication has no such requirement. No connection joins a step to itself, and none closes a cycle.

**State.** The expansion is immutable once made, with ports indexed by step and by type and the two
candidate questions memoised. The connections are the only mutable thing, held beside a cached
reachability closure extended when a connection joins two steps, and cached categories dropped the
moment a connection is added because a new feeder can turn a producer into an endofunctor. Both are
caches: every rule reads as a pure function of the expansion and the wiring so far.

## 6. Contract

```
WorkflowContractIR    schema_version, workflow, workflow_fingerprint, provenance
WorkflowDefinitionIR  contributions, connections
ContributionIR        reference, runtime fields, variables, steps
ConnectionIR          input_id, output_id
```

Identities in the contract are the generated ones: `module_id.step_name` for a step, that with the
input or output name on the end for a connection. The contract carries the definition alone: how a
connection came to be made stays in the assembler's report. `workflow_fingerprint` is the SHA-256 of
the serialised contributions and connections, so a step name, input name, type, contribution order,
module data or connection changes the contract of every build.

IR models are frozen pydantic (`extra="forbid"`, `strict=True`) with patterns on module ids, type
namespaces and runtime field keys, and they round-trip exactly. Variables travel as opaque JSON the
contributing module's executor reads.

## 7. Execution

`build(contract, runtime=None, *, output_directory, working_directory, temporary_directory, monitor)`
runs a frozen workflow, writing `workflow_contract.json` before executing and `build_report.json`
after, and returns a `WorkflowReport`. Setup opens DuckDB (`memory` or `disk`, threads, memory limit,
compression), builds `ExecutionServices`, and validates each module's runtime configuration against its
declared runtime fields.

The run is a wavefront: each round, every pending step whose producers have all completed is handled.
Inputs are grouped by the step's own input, so an open input's entries appear beside each other, and each
contribution is classified by its producer's status:

- `ContinuableInput` — producer succeeded or warned; carries the artifact when there is one.
- `DisruptingInput` — producer failed or was skipped; carries the failure.

A step with any disruption gets `handle_disrupted(context)`, whose base implementation skips the step;
otherwise `handle(context)`. An exception becomes a `FAILED` outcome with a `Failure`. Outcomes are
checked: they answer the step they were asked for, artifacts appear only on declared outputs, and each
artifact's type matches what that output declares.

Failure propagation is per step: a `FAILED` step's active failures are its own plus those it inherited,
a `SKIPPED` step inherits without adding, a succeeded or warned step clears them. Because every output
has a reader, a failure travels to the end of the graph, so what matters is whether anything downstream
absorbed it: failures still active at a step that publishes are `unresolved_failures`, the rest are
`recovered_failures`, and `WorkflowReport.succeeded` means there were none. A step's publication
artifacts become `published_artifacts`.

```python
class ExecutableModule(Protocol):
    ID: ClassVar[str]
    VERSION: ClassVar[str]
    @classmethod
    def create_executor(cls, context: ExecutorFactoryContext) -> ModuleExecutor: ...

class ModuleExecutor(ABC):
    def handle(self, context: ExecutionContext) -> StepOutcome: ...
    def handle_disrupted(self, context: DisruptedExecutionContext) -> StepOutcome: ...  # skips
```

Executors are created once per module and reused for its steps, and are handed that module's variables
at construction. `ExecutionContext.services` gives `logger`, `relations` (`reference`, `view`,
`materialize`, `query`, `export_parquet`, `register_filesystem`, checkpointed by `finish_step`),
`output_storage`, `working_storage`, `temporary_storage` and `credentials`. `WorkflowExecutionMonitor`
receives `start`, `step_started`, `step_finished`, `log`, `workflow_finished`, `workflow_halted` and
`stop`; `NullWorkflowMonitor` is silent, `RichWorkflowMonitor` draws a terminal UI, and the choice
follows an interactive terminal or the `monitor` argument.
